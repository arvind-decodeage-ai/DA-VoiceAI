# M3 plan — Call state, Greet/Wrap, JSON output

**Status:** awaiting approval. No implementation started.
**Depends on:** M1 (closed 2026-09-15, `M1_STATUS.md`), M2 (complete, `M2_PLAN.md`, T6 teardown verified).

## Objective

PRD §10 M3: `CallState`, `EventLog`, `JSONBuilder`; GreetAgent (identify, language) →
WrapAgent (summary, CSAT, `end_call`); JSON written to `./out/` and viewable in the UI.

**PRD acceptance:** JSON validates against the §8 schema; `qa[]` contains every
question/answer pair with correct `turn_idx` and `ts`; `end_call` waits for TTS flush
before closing.

M3 is also where the persistence gap identified during M2 closes — designed in, not
bolted on.

## In scope

- `agent/state.py` — `CallState` and slot schemas (Pydantic)
- `agent/events.py` — `EventLog`: append-only, typed, monotonic
- `agent/output.py` — `JSONBuilder`: pure function over the EventLog
- `agent/agents/greet.py`, `agent/agents/wrap.py` and their prompts; a two-stage machine
  whose transition is enforced in code
- `agent/prompts/base_persona.md` — trim the adopted rewrite (D1)

- `GET /calls/{id}/json` in `api/`, and a JSON viewer panel in `web/`

## Architecture / data flow

```
             ┌──────────── AgentSession[CallState] ────────────┐
   mic ─────▶│  GreetAgent ──(code-gated handoff)──▶ WrapAgent │─────▶ speaker
             │                               tools: record_csat,│
             │                                      end_call    │
             └───────┬─────────────────────────────────┬────────┘
                     │ session events                  │ explicit writes
                     ▼                                 ▼
              ┌─────────────────── EventLog ───────────────────┐
              │ append-only, seq + ts, typed payloads          │  <- single source of truth
              └───────┬──────────────────────────────┬─────────┘
                      │ on end_call                  │ on end_call
                      ▼                              ▼
              Postgres: calls/turns/events/slots   JSONBuilder (pure)
                                                     │
                                     ./out/<call_id>.json
                                                     │
                                     GET /calls/{id}/json ──▶ UI viewer panel
```

**The central commitment:** `EventLog` is the source of truth. `CallState` is live mutable
convenience for the agents; the JSON and the database rows are both *projections* of the
same log. The JSON is derived, never recalled by the LLM (PRD §8: "Built deterministically
from EventLog. Never generated by asking the LLM to recall."). One producer, three
consumers, so they cannot disagree.

## Data model

### CallState

Pydantic model held in `session.userdata`, reachable from every agent and tool through
`RunContext.userdata`:

```
call_id, started_at, language, stage
caller: {name, phone, customer_id}
identity_confirmed: bool
slots: dict[str, SlotValue]        # value + set_at + by_agent
csat: int | None
resolution: {status, summary, ticket_id}
```

`turn_idx` is owned by the EventLog, not CallState, so there is exactly one counter.

### EventLog

Append-only list of `Event(seq, ts, type, payload)`. `seq` is monotonic and assigned on
append; entries are never mutated or removed.

M3 event types: `call_started`, `user_turn`, `agent_turn`, `slot_set`, `agent_handoff`,
`csat_recorded`, `call_ended`. Reserved but unused in M3: `tool_call`, `guardrail_hit` —
declared now so M4/M6 add producers rather than reshaping the log.

Sources: `conversation_item_added` and `user_input_transcribed` (both proven reliable —
the M1 harness has read them across every run since M1), plus explicit writes from the
Wrap tools.

### Persistence

**Write at the end of the call, in one transaction.** Per-event streaming and a background
write queue were both considered and deliberately not adopted: nothing measured says the
turn path needs protecting from a write that does not happen during a turn, and neither
mechanism earns its complexity today.

The shape:

1. **Call start** — insert the `calls` row (`id`, `started_at`, `language`,
   `status='in_progress'`). One write, before any conversation, so an abandoned or crashed
   call still leaves a visible record rather than nothing.
2. **During the call** — no database access at all. The EventLog accumulates in memory.
   Zero turn-path risk, by construction.
3. **On `end_call`** — one transaction writes `turns`, `events` and `slots` from the
   EventLog, and finalises the `calls` row (`ended_at`, `duration_s`, `status`, `result`).

**Known trade-off, accepted:** a crash mid-call loses that call's turns, leaving only the
`in_progress` row. This is the simple-and-reliable choice for a desktop prototype. Because
every writer reads from the EventLog rather than from scattered state, switching to
per-event streaming later is a change in one module, not a redesign. Revisit if in-flight
call loss ever becomes a real problem in practice, not before.

### Schema change (D4)

One addition, in the M0 migration's existing idempotent style so `python db/migrate.py`
stays safe to re-run:

```sql
ALTER TABLE calls ADD COLUMN IF NOT EXISTS result JSONB;
```

`calls.result` holds the built §8 document whole. The normalized tables stay the queryable
projection; `result` is the authoritative artifact and the home for §8 fields that have no
column (`csat`, `resolution`, `compliance_flags`, `latency`, `recording_url`).

## State/event design

Two stages, transition enforced in code — PRD §5: *"This is enforced in code, not in the
prompt."*

```
GreetAgent ──▶ [gate: identity_confirmed AND caller.name set] ──▶ WrapAgent ──▶ end_call
```

The handoff is a `function_tool` on GreetAgent that checks the gate, appends
`agent_handoff` to the EventLog, updates `CallState.stage`, and returns the next agent.
When the gate fails the tool refuses and the agent keeps collecting — the model cannot talk
its way past it. The gate is a single predicate function so M4 replaces it with per-intent
required slots without restructuring the machine.

`end_call` calls `RunContext.wait_for_playout()` before closing — the framework's own
primitive, which is the PRD's "TTS flush before closing", not a sleep.

Room teardown reuses the verified M2 T6 path (D6): the agent leaves, the browser observes
the disconnect and calls `DELETE /calls/{id}`. No new room-closing mechanism.

## Open items carried into T5 scoping

Both surfaced during T4 verification, when a real console call hit a Groq ITPM
429 mid-generation. Recorded here rather than resolved, so T5 scopes them
deliberately.

**1. No event type covers a silent mid-generation failure.** When an LLM stream
dies part-way, the framework commits the text that was actually spoken
(`forwarded_text`, `agent_activity.py:3613`) and stamps the message
`interrupted=speech_handle.interrupted` — which is **False**, because nothing
interrupted it: `perform_llm_inference` closes the text channel when the task
ends, the segment loop sees `ChanClosed`, and the reply exits along its normal
path. The turn is therefore logged as an ordinary completed `agent_turn` holding
a truncated sentence, and the error itself is swallowed by
`AgentSession._on_error` for the first `max_unrecoverable_errors` occurrences.
None of the seven M3 types fit this, and neither reserved type does either
(`tool_call` and `guardrail_hit` mean something else). Adding a type is a
log-shape decision, so it is deferred rather than assumed.

T4 captures what *is* knowable at commit time: `agent_turn.payload.interrupted`,
read off the ChatMessage. That distinguishes barge-in truncation, and it had to
be captured there because the flag is unrecoverable afterwards. It does **not**
cover the failure case above.

**2. An unpaired `user_turn` before `call_ended` is a legitimate shape.** LLM
failure, a crash, a disconnect and a plain hangup all produce a final user turn
with no answer, so JSONBuilder must not assume turns pair up. Proposed rule, to
be confirmed in T5: do not synthesise an empty `qa[]` entry; surface it through
§8's `resolution.status`, whose enum already contains `abandoned`.

## Acceptance criteria / evidence

1. **Schema** — the produced JSON validates against the PRD §8 schema, machine-checked.
2. **`qa[]` completeness** — every question/answer pair present with correct `turn_idx` and
   `ts`, cross-checked against the transcript.
3. **TTS flush** — `end_call` waits for playout; the final audio completes before the room
   closes.
4. **Code-enforced gate** — Greet→Wrap handoff is refused until required slots are filled.
5. **Persistence** — DB rows exist for the call and agree with the JSON document.
6. **UI** — the JSON is viewable in the browser after the call ends.
7. **No regression** — M1 console path clean (harness), M2 browser call still tears down
   cleanly (T6 checks).

M3's evidence is materially stronger than M2's: the JSON file is itself the artifact, backed
by database rows and the worker log. The weaker-evidence risk recorded in the M2 plan closes
here.

## Risks

- **A crash mid-call loses that call's turns** — the accepted trade-off of end-of-call
  persistence, above. The `in_progress` row makes the loss visible rather than silent.
- **§8 fields owned by later milestones** — `compliance_flags`, `guardrail_events`
  (M6), `latency`, `recording_url` (M7). **Approved:** M3 emits them as empty or null, never
  omits them, so the schema check stays stable in shape from M3 through M7 instead of
  changing at every milestone.
- **The M1 dropped-turn bug is still unresolved.** It did not reproduce in the M1 or M2
  acceptance runs, but under M3 it would also mean a missing `qa[]` entry — a data defect,
  not just a silent conversation. `tools/m1_harness.py` stage probes remain available.
- **Persona trimming is a judgement call.** T1 removes capability claims; if the trim goes
  too far the persona loses the warmth that motivated the rewrite, and if not far enough the
  agent promises transfers it cannot perform. Worth reviewing the diff at T1 rather than at
  acceptance.
- **Empty fixtures** — all five fixture files are `[]`. Not an M3 blocker given D2, but M4
  cannot start until they hold real data.
